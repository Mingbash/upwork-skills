# Preferences and effective runs

For one-off analysis use explicit in-chat constraints; no configuration file is required. If the user requests persistence, copy [blank preferences](../assets/preferences.md) only when no preferences file exists. All nulls are intentionally unset; do not import a previous user's values. Explain missing material limits before recommending expenditure. Every workspace run reads the file again; cross-skill options live separately in reference/options.json.

`screen_guard.py config --input <request.json>` accepts `{path, overrides}`; path points to the Markdown preferences, overrides is an optional nested dictionary of complete `{value, mode}` leaves. It reads YAML with safe_load, rejects duplicate keys, unknown keys, invalid leaf types/modes, inverted bounds, malformed periods and invalid score weights; returns the saved version and exact effective copy. It does not save edits. Python 3.9+ and PyYAML are required for this subcommand; if PyYAML is absent, report the dependency rather than silently modifying the environment. The account subcommand uses only the standard library.

Context fields must use context mode. Budget/spending/time numeric limits are nonnegative. Hard budget/rate min greater than hard max, or hard reserve exceeding the observed usable balance, is a hold for that decision. Paired bounds with soft sides express tension rather than unconditional rejection. A set period cap needs explicit start/end. Malformed bounds are config errors; an actual balance below a valid reserve is a screening outcome, not corrupt config. Do not fill unset available hours from contract count.

Supplementary checks remain the agent's responsibility: currency compatibility, timezone validity, feasible overlap/deadlines, mutually exclusive hard eligibility, and score dimensions/thresholds appropriate to the supplied rubric. Stop the affected recommendation when constraints are incoherent. A syntactically valid file does not prove business feasibility.

Use profile and saved config versions plus an exact deep copy of effective settings in each run. A temporary override changes this run only; user requests for lasting changes create a new version of preferences. History stays immutable. Schedule configuration belongs to an outer scheduler and does not create or enable a task by itself.

## Native search filter preferences (additive schema v1 extension)

`platform_filters` is optional for older workspaces; missing fields default to unset on load, without rewriting the file. New templates include the complete group. Each leaf still has value and mode. `feed` uses context and an optional nonempty source-specific feed name (legacy best_match/most_recent values remain accepted). This does not assert platform support. Other leaves are hard/soft: payment_verified (boolean), previous_clients_only (boolean), experience_levels (entry/intermediate/expert), proposal_ranges (lt5/5to10/10to15/15to20/20to50), client_hires (none/1to9/10plus). Multiple selections within one dimension mean OR. Different hard dimensions combine with AND. Null or empty selections mean unrestricted. previous_clients_only=false also means unrestricted, while payment_verified=false explicitly requests unverified clients.

Contract type remains in contract.types (fixed/hourly); do not maintain a contradictory second copy. Payment verification is not proof of hiring intent or safety; entry/expert describes the posting requirement, not a newly asserted freelancer credential. No-hires is observed zero hires, distinct from unavailable history. Native proposal bands are labels, not exact counts; ambiguous boundary evidence stays unknown rather than guessed. Client hire history and hire rate are different measures.

These settings describe user preferences, not proof that platform filters were applied. Only push supported hard constraints into acquisition; keep soft constraints for ranking so they do not silently remove candidates. If a search feed cannot apply a constraint, retain it for local qualification and record that limitation. Historical filter labels are compatibility values, not an exhaustive current UI list. Verify supported approved-API capabilities or supplied source metadata during acquisition; do not invent URL query parameters or count an unsupported filter as applied. Independent needs research never inherits this group.

## Retained candidates and delivery

`search.candidate_count` means the target number of retained strong-fit + actionable watch candidates (apply readiness is a separate strict-mode result), not the number of fetched or inspected postings. In text-only mode, analyze the supplied sample and report any shortfall. With an approved collection source, use the user-agreed collection scope/time budget; stop when the target is met, accessible relevant supply is exhausted, or the collection budget/blocker is reached. Never weaken eligibility to fill the target. A watch must have evidence of fit, a resolvable open condition and an explicit revisit trigger; hard failures remain excluded. Clarify may be retained as watch only when those conditions genuinely hold. Report any shortfall honestly.

Read optional workspace `reference/delivery.json` for user format, template headers and output inclusion preferences. Preserve every assessment internally, including skipped jobs, but omit skipped rows from a shortlist-only deliverable. Keep individual job evidence, phase scope, economic assumptions, scores/unknowns and next action. Default to inline Markdown. Create XLSX only when requested/useful and a compatible tool exists; no spreadsheet skill is mandatory. User-specific template links and output counts belong only to workspace data.
